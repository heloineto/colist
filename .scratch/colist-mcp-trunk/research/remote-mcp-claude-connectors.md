## 1. Spec version and transport

- **Current spec: `2026-07-28`** ([versioning](https://modelcontextprotocol.io/specification/versioning)). Previous: `2025-11-25`.
- 2026-07-28 is **stateless**: no `initialize` handshake, no `Mcp-Session-Id`, no GET stream, no SSE resumability. Every request carries protocol version + client capabilities in `_meta`; servers MUST implement `server/discover`. Cross-call state goes in explicit handles passed as tool args ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md) items 1-4, 9).
- Streamable HTTP (2026-07-28): single endpoint, POST only; response is `application/json` or a per-request `text/event-stream`. GET/DELETE from old clients: answer `405`; ignore `Mcp-Session-Id`. Required headers per POST: `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` (for `tools/call` etc.), and server MUST reject header/body mismatch with `400` + `-32020`. Server MUST validate `Origin` if present (403 on invalid) ([transport](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http.md)).
- **HTTP+SSE (2024-11-05) is formally Deprecated** (since 2025-03-26, reclassified under the lifecycle policy in 2026-07-28); new implementations SHOULD NOT adopt it ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md) "Deprecated" 2).
- **What Claude speaks today:**
  - claude.ai docs say: use Streamable HTTP; legacy HTTP+SSE still supported but being deprecated; for OAuth Claude follows the **2025-03-26, 2025-06-18 and 2025-11-25** authorization specs ([building](https://claude.com/docs/connectors/building.md)). Anthropic's 2026-07-28 support is "rolling out across Claude products" with no per-surface dates ([blog](https://claude.com/blog/bringing-mcp-2026-07-28-to-claude)). Claude's own lazy-auth example server still uses an `initialize` + stateless (`sessionIdGenerator: undefined`, `enableJsonResponse: true`) SDK transport ([lazy auth](https://claude.com/docs/connectors/building/lazy-authentication.md)).
  - Claude Code v2 runtime (default on v2.1.232+/v2.1.274+) probes HTTP and claude.ai connector servers for 2026-07-28 and uses it when supported, else falls back to the 2025 handshake. Env: `MCP_SDK_GENERATION=v1|v2`, `MCP_PROTOCOL_NEGOTIATION=auto|legacy` ([Claude Code MCP](https://code.claude.com/docs/en/mcp), "MCP client runtimes").
  - Unconfirmed user report: claude.ai connector traffic from Desktop/Claude Code sent a 2026-07-28 body with a 2025-11-25 header, which strict servers reject with `-32020` ([claudeissues #93290](https://claudeissues.com/issue/93290-bug-claude-desktop-claude-code-cli-send-mcp-protocol-version-2025-11-25-with-met)). Not from Anthropic; treat as a risk to test for.
- So **serve both eras**: TS SDK v2 serves 2025-era clients only through `*StreamableHTTPServerTransport`; to serve both, use `createMcpHandler(() => createServer())`. `createMcpHandler` checks no `Host`/`Origin`, so mount that check yourself ([SDK upgrade guide](https://github.com/modelcontextprotocol/typescript-sdk/blob/v2.4.0/docs/migration/upgrade-to-v2.md) step 7).

## 2. Authorization (spec 2026-07-28)

- Optional overall; if used on HTTP, SHOULD conform. AS MUST implement **OAuth 2.1** ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization.md)).
- **Protected Resource Metadata (RFC 9728): MCP server MUST implement.** PRM MUST list at least one `authorization_servers` entry. Server MUST offer at least one discovery path ([AS discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery.md)):
  1. `WWW-Authenticate: Bearer resource_metadata="..."` on `401`, or
  2. well-known, **path-inserted** first: MCP at `https://example.com/public/mcp` means `https://example.com/.well-known/oauth-protected-resource/public/mcp`, then root `https://example.com/.well-known/oauth-protected-resource`.
  Clients use the header when present, else probe in that order.
- **AS metadata**: RFC 8414 or OIDC Discovery (AS MUST provide one, clients MUST try both). For an issuer with a path (`https://auth.example.com/tenant1`) clients try `/.well-known/oauth-authorization-server/tenant1`, then `/.well-known/openid-configuration/tenant1`, then `/tenant1/.well-known/openid-configuration`. The doc's `issuer` MUST equal the issuer used to build the URL ([AS discovery](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/authorization-server-discovery.md)).
- **PKCE**: clients MUST use S256 and MUST refuse if `code_challenge_methods_supported` is absent from AS metadata ([security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations.md)).
- **Resource indicators (RFC 8707)**: clients MUST send `resource` = canonical MCP server URI (e.g. `https://mcp.example.com/mcp`, no trailing slash, no fragment) on both authorize and token requests. **Servers MUST validate the token audience is themselves** and MUST NOT accept or pass through any other tokens ([authorization](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization.md) "Token Handling").
- **401/403**: invalid/expired token gives `401`; insufficient scope gives `403` + `WWW-Authenticate: Bearer error="insufficient_scope", scope="...", resource_metadata="..."`. Servers SHOULD put `scope` in the `401` challenge; otherwise clients request PRM `scopes_supported`. Servers SHOULD NOT list `offline_access` in PRM. Tokens only in the `Authorization` header, never query string.
- **`iss` (RFC 9207)**: AS SHOULD return `iss` in authorization responses and advertise `authorization_response_iss_parameter_supported: true`; future revision expected to make it MUST.
- **Client registration** ([client registration](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration.md)):
  - Priority: pre-registered, then **CIMD** (if AS advertises `client_id_metadata_document_supported: true`), then DCR (if `registration_endpoint`), then prompt user.
  - **CIMD is preferred (SHOULD)**; **DCR is Deprecated** in 2026-07-28, kept for backward compat ([changelog](https://modelcontextprotocol.io/specification/2026-07-28/changelog.md) "Deprecated" 4).
  - CIMD AS duties: fetch the URL `client_id`, MUST check doc `client_id` equals URL, MUST validate `redirect_uri` against doc, SHOULD cache per HTTP headers, mind SSRF, MUST show redirect hostname on consent.
- **Refresh**: AS MUST rotate refresh tokens for public clients; SHOULD issue short-lived access tokens ([security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations.md)).

### What Claude actually does ([auth for connectors](https://claude.com/docs/connectors/building/authentication.md))

- Same auth stack for claude.ai, Desktop, mobile, Cowork, Claude Code.
- Needs a real **`401`** with `WWW-Authenticate` (ignored on `200`; a `200` + `isError` "please sign in" never triggers sign-in). `resource_metadata` may point to any HTTPS URL, not just the MCP origin. Fallback probe: `/.well-known/oauth-protected-resource/<mcp-path>` then root.
- PRM `resource` must equal the URL the user typed, including path. **Only the first `authorization_servers` entry is used.**
- AS metadata: tries `/.well-known/oauth-authorization-server`, then `/.well-known/openid-configuration` ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting.md)).
- Registration types: `oauth_dcr`, `oauth_cimd` (both default), `oauth_anthropic_creds` (directory listings), `custom_connection`, `static_headers` (beta), `none`.
- **CIMD is used only if AS metadata has both `client_id_metadata_document_supported: true` and `"none"` in `token_endpoint_auth_methods_supported`**; otherwise falls back to DCR. Claude's CIMD client is a public client (PKCE, no secret). DCR creates a new client on every fresh connection.
- Claude Code CIMD: `https://claude.ai/oauth/claude-code-client-metadata` (fetched 2026-11-15: `redirect_uris` `http://localhost/callback`, `http://127.0.0.1/callback`, `token_endpoint_auth_method: none`, grants `authorization_code`, `refresh_token`). The claude.ai CIMD URL is not documented; the AS learns it from the `client_id` it receives.
- Always sends PKCE S256 and RFC 8707 `resource` (canonical form: lowercase scheme/host, no trailing slash, no default port). Validate `aud` against the canonical value ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting.md)).
- Scopes: `401` `scope` param, else PRM `scopes_supported`; appends `offline_access` if AS metadata lists it. Step-up via `403 insufficient_scope` works (inline re-auth, then retry).
- **User-pasted client id/secret: yes.** The custom connector dialog has "OAuth client": *Use Claude's published identity* (CIMD, recommended), *Register automatically* (DCR), or *Use your own OAuth client* (client ID, optional secret; register `https://claude.ai/api/mcp/auth_callback`) ([add-unlisted](https://claude.com/docs/connectors/custom/add-unlisted.md)). Auth settings can't be edited later; remove and re-add.
- `client_credentials` (machine-to-machine) is not supported.
- Discovery metadata cached globally per URL for about 5 min.

## 3. claude.ai specifics

- **Plans**: custom connectors on Free, Pro, Max, Ultra, Team, Enterprise. **Free: one custom connector.** Team/Enterprise: an Owner adds it org-wide, members connect individually ([help center](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp), [add-unlisted](https://claude.com/docs/connectors/custom/add-unlisted.md)).
- **Add**: Customize > Connectors > Add > Add custom connector, enter name + URL, keep "Detected" auth options, Add, Connect.
- **Mobile**: connections run from Anthropic's cloud "across every Claude client, including claude.ai, Claude Desktop, Cowork, and the mobile apps" ([help center](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Added once, usable on mobile. Same callback URL for web, Desktop, mobile, Cowork.
- **Callback URLs to allowlist**: `https://claude.ai/api/mcp/auth_callback` (hosted apps). Claude Code: loopback `http://localhost:<any>/callback` and `http://127.0.0.1:<any>/callback`, matched port-agnostically ([auth](https://claude.com/docs/connectors/building/authentication.md)). A third-party summary says the callback may move to `https://claude.com/api/mcp/auth_callback`; not in current Anthropic docs, cheap to allowlist too.
- **Network**: outbound from `160.79.104.0/21` (connector doc) and also `153.61.208.0/20` (platform IP page) ([IPs](https://platform.claude.com/docs/en/api/ip-addresses)). The AS host must be reachable from the same range. **Port 443 only. IPv4 only: hostname needs a public `A` record**; every resolved address must be globally routable. **Cross-host redirects drop `Authorization`**, so register the exact final URL ([troubleshooting](https://claude.com/docs/connectors/building/troubleshooting.md)).
- **Token refresh**: reactive on `401`, proactive up to 5 min before expiry. Return `invalid_grant` for dead refresh tokens; rotate refresh tokens for public clients (return the new one in the same response). `/token` must accept `application/x-www-form-urlencoded`. Timeouts: 10 s for discovery/registration/token, 30 s for refresh ([auth](https://claude.com/docs/connectors/building/authentication.md)).
- **Tool annotations**: every tool should have `title` plus `readOnlyHint: true` (read-only) or `destructiveHint: true` (modifies/deletes). "These determine auto-permissions in Claude. Read-only tools can run without per-call confirmation, and destructive tools always prompt." Separate read and write tools (no catch-all). Tool names 64 chars or fewer ([review criteria](https://claude.com/docs/connectors/building/review-criteria.md); written for directory review but describes client behavior). Users can set a tool to Always allow or Blocked; **Research mode calls connector tools without further approval** ([help center](https://support.claude.com/en/articles/11175166-getting-started-with-custom-connectors-using-remote-mcp)). Spec: clients MUST treat annotations as untrusted unless the server is trusted ([tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).
- **Limits**: tool result up to about **150,000 characters**; **240 s** per tool call ([building](https://claude.com/docs/connectors/building.md)).
- **Features**: tools, prompts, resources (text + binary), text and image tool results, MCP Apps (interactive UI). **Not supported**: resource subscriptions, sampling, "advanced or draft capabilities" ([building](https://claude.com/docs/connectors/building.md)).

## 4. Claude Code ([MCP docs](https://code.claude.com/docs/en/mcp))

- `claude mcp add --transport http <name> <url>`, optional `--header "Authorization: Bearer ..."`, `--scope local|project|user`. `.mcp.json` `type` accepts `http` or `streamable-http`. SSE transport is deprecated; Claude Code tries HTTP first.
- OAuth: `/mcp` in a session, or `claude mcp login <name>` / `logout`. Tokens stored securely and refreshed automatically. Supports DCR and **CIMD (auto-discovered)**. Pre-registered client: `--client-id`, `--client-secret` (masked prompt or `MCP_CLIENT_SECRET`), `--callback-port` to pin the loopback port. `oauth.authServerMetadataUrl` overrides discovery.
- Also picks up the user's claude.ai connectors automatically.
- Limits: warning above 10k tokens, cap 25k tokens (`MAX_MCP_OUTPUT_TOKENS`); `MCP_TOOL_TIMEOUT`; 5 min idle timeout for HTTP servers. Resources via `@` mentions; prompts supported; `list_changed` honored.
- Annotations: `readOnlyHint` lets read-only calls run in parallel; `readOnlyHint` or `idempotentHint` lets Claude Code retry a call once after a dropped connection. `_meta["anthropic/requiresUserInteraction"]: true` forces a prompt on every call.

## 5. Security guidance relevant to a small app

- **No token passthrough**: MCP server MUST only accept tokens issued for itself (audience) and MUST NOT forward the client's token upstream ([security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations.md)). Since Colist's MCP server calls its own domain code in-process, there is no upstream token at all.
- **Confused deputy** applies to MCP proxies that use a static client ID at a third-party AS: they MUST get per-client user consent. Not Colist's case (own AS), but Colist's AS should still show a consent screen naming the client (CIMD host, not self-asserted `client_name`) and the redirect hostname, with an extra warning for loopback-only clients ([lazy auth](https://claude.com/docs/connectors/building/lazy-authentication.md), [security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations.md)).
- Exact redirect URI matching (loopback ports excepted); `state`; HTTPS everywhere; SSRF guard on CIMD fetch (only `https`, block private IPs, size/time limits); short-lived access tokens; refresh rotation.
- Validate `Origin` on the MCP endpoint (403 if present and bad).
- Prompt injection: tool descriptions must describe, not instruct; tool output (user-entered item names) is untrusted text for the model ([review criteria](https://claude.com/docs/connectors/building/review-criteria.md)).
- Authorize every handle (list id, item id) per call against the token's user; ids are names, not capabilities ([tools: stateful tools](https://modelcontextprotocol.io/specification/2026-07-28/server/tools.md)).

## Implications for Colist

- **Endpoint**: `https://colist.heloineto.com/api/mcp`, POST only, stateless, JSON responses (no SSE needed). Serve 2026-07-28 and 2025-11-25 (TS SDK v2 `createMcpHandler`, plus our own `Origin` check). No sessions to store, fits current single-instance API.
- **Discovery**: return `401` + `WWW-Authenticate: Bearer resource_metadata="https://colist.heloineto.com/.well-known/oauth-protected-resource/api/mcp", scope="..."`. Serve PRM there and at root, with `resource: "https://colist.heloineto.com/api/mcp"`. Caddy currently routes `/api`; it must also route `/.well-known/oauth-protected-resource*`, `/.well-known/oauth-authorization-server*` and `/.well-known/openid-configuration*` to the API (or put PRM under `/api` via the header pointer; AS metadata still lives under the issuer host's root well-known path). No apex/www redirects on these URLs.
- **AS**: Colist must become an OAuth 2.1 AS for its own users, logging in via the existing better-auth cookie session on the consent page. Metadata needs `issuer`, `authorization_endpoint`, `token_endpoint`, `code_challenge_methods_supported: ["S256"]`, `client_id_metadata_document_supported: true`, `token_endpoint_auth_methods_supported` including `"none"`, `grant_types_supported: ["authorization_code","refresh_token"]`, ideally `authorization_response_iss_parameter_supported: true` + `iss`. **CIMD alone covers claude.ai, mobile and Claude Code**; skip DCR (deprecated, and Claude only falls back to it). Whether better-auth's OAuth provider plugin supports CIMD + `resource`/audience is an open question for the auth research ticket.
- **Redirect allowlist** (enforced via CIMD docs anyway): `https://claude.ai/api/mcp/auth_callback`, loopback `localhost`/`127.0.0.1` any port. Optionally restrict accepted CIMD hosts to `claude.ai` (trust policy) since only Claude is targeted.
- **Tokens**: access tokens bound to `aud = https://colist.heloineto.com/api/mcp`, short-lived; rotating refresh tokens; `invalid_grant` on reuse/expiry; form-urlencoded `/token`; respond in well under 10 s.
- **Network**: ensure `colist.heloineto.com` has a public IPv4 `A` record on 443; don't block `160.79.104.0/21` / `153.61.208.0/20` with rate limits.
- **Tools**: separate read (`readOnlyHint: true`) and write tools (`destructiveHint: true` on deletes; `idempotentHint` where true, e.g. set checked state). Short names, `title` on each, deterministic order, keep results under about 150k chars. Tools-only is enough for v1; resources/prompts optional.
- **Plans**: users on Free can add Colist as their one custom connector; nothing to configure per user beyond the URL.
