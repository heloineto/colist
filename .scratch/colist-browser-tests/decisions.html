Playwright de verdade contra a API de verdade, em todo PR.

Pesquisei e decidi tudo sozinho, como você pediu, copiando o padrão do voto-a-voto/apps/web onde ele serve. Onde o Colist é diferente, eu diverjo e explico o porquê. Desmarque a decisão que quiser mudar, escreva o que prefere, e copie tudo no botão de baixo para colar no Claude.

Unit

Vitest 5, os 4 specs de hoje em src/**/*.spec.ts.

E2E

Playwright em apps/web/e2e/, Chrome desktop e celular.

CI

Job novo E2E (web), obrigatório para merge.

Uma interpretação minha: li "Vitest para testar testes end-to-end que seria com Playwright mesmo" como: e2e roda no runner do Playwright e unitário roda no Vitest. O voto-a-voto também usa o Vitest em modo browser, mas só para rodar as stories do Storybook, e o Colist não tem Storybook. Se você queria testes de componente no browser com o Vitest, desmarque a primeira decisão.

Decisão 2

Contra o que o browser roda

O voto-a-voto aponta para um backend compartilhado com uma conta real. O Colist não tem staging (merge = produção), então o Playwright sobe tudo sozinho: um Postgres descartável, a API em modo teste e o Vite.

Decisão 3

O que o primeiro lote testa

O critério: o que você usa todo dia, passando pelos componentes do Mantine que mais quebram num upgrade (inputs, Checkbox, Modal, Menu, Combobox, Notifications).

Spec Cobre

Fica para um segundo lote: histórico, editar perfil, apps conectados + tela de consentimento OAuth, troca de idioma, modo offline, feedback com anexo (precisa de S3). Login com Google fica fora (precisaria de credenciais reais do Google).

Decisão 4

Roda no CI em todo PR

O voto-a-voto não roda o e2e do web no CI, porque precisa de uma conta real num backend real. No Colist o e2e é autocontido, e o motivo de tudo isso é barrar upgrade quebrado do Dependabot antes do merge, que já é deploy.
